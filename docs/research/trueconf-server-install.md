# TrueConf Server для интеграционного тестирования n8n-ноды: план установки

Дата исследования: 2026-11-15. Источники — официальная документация TrueConf (docs.trueconf.com / trueconf.com/docs), база знаний, mirror.trueconf.ru, GitHub TrueConf, Docker Hub. Все ссылки — в конце документа.

Целевая задача: поднять тестовый TrueConf Server, на котором n8n-нода сможет подключиться к **Chatbot Connector** (HTTP API + WebSocket, порт 4309) и прогнать сценарии «отправить сообщение / получить событие / кнопки / файлы».

---

## 0. Краткий вывод (TL;DR)

* Нужна **TrueConf Server Free** — Chatbot Connector (API чат-ботов) входит в неё **бесплатно начиная с версии 5.5.0**; отдельного расширения/лицензии на ботов нет, служба `trueconf-bridge` ставится вместе с сервером.
* Free-лицензия: до **1000 онлайн-пользователей**, **10 PRO**, 1 гость, 1 SIP/H.323; бессрочная, но **продлевается ежегодно** и **требует постоянного доступа в интернет** к `reg.trueconf.com:4310` (иначе сервер отключается через 12 ч; офлайн-регистрации во Free нет).
* Linux-пакеты: `.deb` (Debian 11/12/13, Astra SE 1.7/1.8, РЕД ОС 7.3/8) и `.rpm` (CentOS Stream 9, **Альт Сервер c10f1/10/11**). Плюс официальный Docker-образ `trueconf/trueconf-server`.
* ALT Linux 11.1 — **официально поддерживается** (ветка p11 в репозитории вендора), это делает вариант «поставить рядом с n8n на 192.168.0.11» легальным и самым дешёвым по трудозатратам.
* Рекомендация: **(a) 192.168.0.11 рядом с n8n**, при условии ≥8 ГБ RAM и свободных портов 80/443/4307; запасной вариант — **(c) Docker Desktop на dev-машине 192.168.0.10**.

## 1. Редакции TrueConf Server и ограничения Free

### 1.1 Линейка

| Редакция | Позиционирование | Ключевое |
|---|---|---|
| **TrueConf Server Free** | бесплатный self-hosted сервер для мессенджера и небольших конференций | 1000 онлайн-пользователей, 10 PRO, 1 гость, 1 SIP/H.323/RTSP; бессрочная лицензия с ежегодным продлением; обязательный онлайн-контроль лицензии |
| **TrueConf Server Standard** | платно, до 1000 пользователей (SMB) | лицензируется по PRO- и online-пользователям; снимает ограничения Free, включает федерацию, офлайн-регистрацию, поддержку |
| **TrueConf Enterprise** | платно, свыше 1000 пользователей, распределённые организации | кластер/балансировка, TrueConf Directory, License Manager, Border Controller, интеграция с DLP; в Enterprise нет деления на PRO/online — все авторизованные могут входить в конференции |

Дополнительно у сервера есть расширения, часть которых платная и не входит во Free (важно, чтобы не планировать лишнего): федерация — только с любой платной лицензией, водяной знак — платно, UDP Multicast — платно, live streaming — с пакетом поддержки, DLP/Directory/License Manager/Border Controller — только Enterprise. LDAP/AD, сурдоперевод, SIP-шлюз (1 подключение) — доступны и во Free.

### 1.2 Ограничения Free (по данным страницы продукта и руководства администратора)

* **Онлайн-пользователи: до 1000** — одновременно авторизованные пользователи; имеется в виду мессенджер (личные и групповые чаты, файлы) и звонки 1-на-1.
* **PRO-пользователи: 10** — только они могут участвовать в групповых конференциях; остальные — чаты и звонки «точка-точка».
* **Гостевые подключения: 1**, **SIP/H.323/RTSP: 1**.
* Число **зарегистрированных** учёток не ограничено (ограничение — на одновременные подключения).
* Лицензия **бессрочная, но продлевается раз в год** через сайт вендора; ключ выдаётся на корпоративную почту.
* **Постоянное соединение с `reg.trueconf.com` по TCP 4310** для проверки лицензии. При обрыве связи Free-сервер **отключается через 12 часов**; в панели показывается время отключения. Прокси не поддерживается.
* **Офлайн-регистрация во Free недоступна** (только платные/триальные лицензии).
* Федерация между серверами — платно (для схемы «отдельный сервер под ботов + федерация с основным» нужна платная лицензия).

### 1.3 Chatbot Connector во Free — КЛЮЧЕВОЙ ПУНКТ

* API чат-ботов **поставляется в составе TrueConf Server с версии 5.5.0** (не отдельный продукт и не отдельный дистрибутив).
* Официальное подтверждение поддержки во Free — в README библиотеки `python-trueconf-bot`: *«Chatbot features are supported in TrueConf Server 5.5 or above, TrueConf Enterprise, and TrueConf Server Free»*.
* Служба **`trueconf-bridge`** (TrueConf Bridge) входит в состав сервера и ставится вместе с ним; отдельного расширения «Chatbot Connector» в разделе **Extensions** панели управления нет, включать нечего — достаточно, чтобы служба была запущена.
* Технические лимиты: **до 128 одновременных WebSocket-соединений** (с 5.5.3), JWT-токен живёт **1 месяц**, с 5.5.4 один токен можно использовать в нескольких WS-соединениях.
* Боты — это **обычные учётные записи сервера** (Registry или LDAP), они расходуют online-лицензии. При лимите Free в 1000 онлайн-пользователей 1–10 ботов — не проблема; отдельной «лицензии на ботов» не существует.

Практический вывод: **для тестов n8n-ноды Free полностью достаточно** — ни одна функция Chatbot Connector (чаты, сообщения, файлы, кнопки, опросы, события) не урезана редакцией; упираться можно только в 10 PRO, если параллельно тестировать групповые конференции.

## 2. Где скачать

### 2.1 Официальная точка входа (обязательная форма)

* EN: <https://trueconf.com/downloads/trueconf-server/>
* RU: <https://trueconf.ru/downloads/trueconf-server/>

Схема: заполнить форму (компания, отрасль, ФИО, **корпоративная** почта, телефон, страна) → на почту приходит **регистрационный ключ в течение ~15 минут** → на странице после формы выбираются вкладки **Windows / Linux / Docker** и скачивается установщик. Бесплатную версию выдают только на корпоративный e-mail; личный (gmail и т.п.) может быть отклонён.

Прямые ссылки на файлы не публикуются (они генерируются после формы), поэтому в плане установки нужно заложить шаг «получить ключ и скачать пакет» как отдельную задачу с ожиданием.

## 3. Системные требования и порты

### 3.1 Железо (официально)

| Параметр | Начальная конфигурация | Рекомендуемая |
|---|---|---|
| CPU | x86-64, ≥4 логических ядер, PassMark > 7000 (пример: i3-8100 / i5-7400 / Xeon E-2234) | ≥16 логических ядер, PassMark > 14000 (i7-10700, Ryzen 7 2700) |
| RAM | **16 ГБ** | 32 ГБ+ |
| Диск | **20 ГБ свободно** (при обновлении — запас ×3 от размера БД) | — |
| Сеть | Ethernet 1 Гбит/с | — |
| IP | **статический** (обязательно) | — |
| Гипервизоры | Hyper-V, Xen, KVM, VirtualBox, VMware Workstation/ESXi | — |

Только x86-64; десктопные гибридные Intel (P+E ядра) вендор не рекомендует. Для теста с одним ботом 16 ГБ не нужны физически, но это неофициальная эксплуатация — на тестовом стенде допустимо, на «почти прод» — нет.

### 3.2 Порты (что реально нужно)

| Порт | Протокол | Назначение | Обязателен для бота? |
|---|---|---|---|
| **80/tcp** | HTTP | первичная настройка, панель до включения HTTPS; по умолчанию панель на 80 или 8888 | да (на время настройки) |
| **443/tcp** | HTTPS | панель, гостевая страница, WebRTC-страницы, **WSS для ботов** (`/websocket/chat_bot/`, `/bridge/api/`) | да, если подключаться по WSS |
| **4307/tcp** | trueconf | медиаданные и передача файлов в чатах | для чат-бота не критично, но нужен клиентам |
| **4309/tcp** | HTTP/WS | **TrueConf Bridge** — «сырой» HTTP API и WebSocket чат-ботов | да, если подключаться напрямую (локально) |
| 4310/tcp (исходящий) | trueconf | к `reg.trueconf.com`, проверка лицензии Free | **обязательно для Free** |
| 443/tcp (исходящий) | HTTPS | к `reg.trueconf.com` (push-уведомления) | желательно |
| 53000–56000 UDP/TCP | WebRTC/SRTP | браузерные конференции | нет |
| 5060/5061, 1718–1720, 52000–52499, 50000–51999 | SIP/H.323/RTP | шлюз | нет |
| 1935/tcp (исходящий) | RTMP | трансляции на YouTube/Wowza | нет |
| 554/tcp (входящий) | RTSP | RTSP-источники | нет |
| 4315/tcp | WebSocket | Calendar Connector | нет |
| 5432 или 5444 | PostgreSQL | локальная БД (порт задаётся при установке; 5444 по умолчанию для отчётов) | только localhost |

Про **8443**: в документации TrueConf он не используется (HTTPS по умолчанию 443, панель 80/8888, БД 5432/5444). Если 8443 упоминается в чьих-то инструкциях — это либо нестандартная настройка веб-порта, либо чужой сервис. Порт **4309** в таблицах «обязательных портов» базы знаний отсутствует именно потому, что он рассматривается как локальный: официально рекомендуется подключать ботов **локально** к `localhost:4309` (без шифрования) либо **снаружи** через `trueconf-web` по 443 (`https://server/bridge/api/`, `wss://server/websocket/chat_bot/`).

### 3.3 Что это значит для n8n

* Если n8n и TrueConf на **одной машине** — идеальный вариант: `http://127.0.0.1:4309/bridge/api/...` и `ws://127.0.0.1:4309/websocket/chat_bot/`, без TLS и DNS.
* Если n8n в **контейнере** — `localhost` внутри контейнера не хост; нужно имя хоста/IP или `host.docker.internal` (Docker Desktop) / `--add-host` (Linux).
* Если TrueConf на **другой машине** — либо `ws://192.168.0.x:4309/...` (нужно убедиться, что Bridge слушает не только loopback: `ss -ltnp | grep 4309`), либо корректный WSS через 443 с валидным сертификатом.

## 4. Процесс установки

### 4.1 Linux (Debian/Ubuntu-совместимые, .deb)

Предусловия:

1. Отдельная (виртуальная) машина, **64-бит**, желательно **без предустановленного веб-сервера** — у TrueConf свой веб-сервер (конфликт за 80/443).
2. OS-пользователь, под которым ставим, **обязан иметь пароль**; его логин попадёт в администраторы панели.
3. **Нельзя**, чтобы в ОС существовал пользователь `trueconf` — пакет создаёт его сам.
4. `sudo apt update && sudo apt upgrade -y && sudo apt install -y gnupg2`.

Установка из файла:

```bash
sudo apt install -yq ./trueconf-server-<версия>.deb
# можно сразу назначить админов панели:
sudo TCADMINS_USERS=main_admin,second_admin apt install -yq ./trueconf-server-<версия>.deb
```

Во время установки debconf спросит логины OS-пользователей-администраторов панели. Если вместо логина ввести несуществующего пользователя, установка падает с `dpkg returned an error code (1)`; лечится `echo PURGE | sudo debconf-communicate trueconf-server` и повторной установкой.

Что появляется в системе:

* каталог **`/opt/trueconf/server`** (`bin`, `etc`, `var/lib`, `var/log`); БД — `/opt/trueconf/server/bin/database/`;
* службы systemd: **`trueconf`** (движок), **`trueconf-db`** (PostgreSQL), **`trueconf-web`** (панель, WebRTC, HTTPS), **`trueconf-manager`**, **`trueconf-php`**, **`trueconf-bridge`** (WebSocket для веб-приложений и **ботов**);
* панель управления: `http://<ip>/` — порт 80, либо 8888, если 80 занят.

Важный нюанс: сразу после установки основной сервис **не стартует** — это нормально, он поднимется после регистрации.

Смена порта панели без переустановки:

```bash
sudo nano /opt/trueconf/server/etc/webmanager/listen.conf      # Listen 8888
sudo nano /opt/trueconf/server/etc/manager/manager.toml        # [web] connection = "http://127.0.0.1:8888"
sudo systemctl restart trueconf-manager trueconf-web
```

### 4.2 Linux RPM (CentOS Stream 9, ALT, РЕД ОС)

CentOS Stream 9 (по документации): отключить SELinux, подключить EPEL, обновиться, затем `sudo dnf install -y ./trueconf-server-<версия>.rpm`.

```bash
sudo sed -i 's/^SELINUX=.*/SELINUX=disabled/g' /etc/selinux/config
sudo dnf install epel-release && sudo dnf update -y
sudo dnf install -y ./trueconf-server-<версия>.rpm
```

Для ALT Linux (apt-rpm) логика та же, что в Debian-ветке: локальный файл `apt-get install ./trueconf-server-*.rpm` либо подключение репозитория вендора. Точный синтаксис rpm-строки для `sources.list` зависит от ветки ALT (в зеркале — `altlinux/p11/x86_64/base`) — на стенде проверить `apt-get update` и при сомнениях ставить из файла.

Astra Linux SE: пакет `.deb`, ставится с выключенным режимом защищённой сети (ЗПС), т.к. postinst инициализирует БД и импортирует ключ подписи; вендор имеет совместные протоколы испытаний с Astra (версии 5.4.x/5.5.x).

### 4.3 Windows

* Мастер установки (GUI), ~1 минута. Спрашивает **Web TCP port** (панель) и **TCP port БД** (по умолчанию 5444; **после установки изменить нельзя**, только переустановка).
* Каталог по умолчанию `C:\TrueConf` (рабочий каталог, БД — `C:\TrueConf\database`).
* Службы: **TrueConf Server**, **TrueConf Database**, **TrueConf Web Manager**, **TrueConf Server Manager**, **TrueConf Bridge**.
* Требования к ОС: Windows Server 2012–2025 или Windows 10/11 **Pro/Enterprise**; пользователь ОС с паролем; не иметь пользователя `trueconf`.
* **Тихих ключей установщика в документации нет** — описан только интерактивный мастер. Автоматизировать развёртывание на Windows логичнее через Docker Desktop, а не через silent-install.

### 4.4 Docker (в т.ч. Docker Desktop на Windows)

```bash
docker run -d --name vcs_server \
  -p 80:80 -p 443:443 -p 4307:4307 -p 4310:4310 \
  -e ADMIN_USER=tc_admin -e ADMIN_PASSWORD='<пароль>' \
  -v /home/$USER/trueconf/server/lib:/opt/trueconf/server/var/lib \
  trueconf/trueconf-server:stable
```

(в статье вендора порядок аргументов с `--name` после имени образа — фактически `--name` должен идти до образа, иначе Docker воспримет его как команду контейнера).

Полезные переменные:

* `ADMIN_USER` / `ADMIN_PASSWORD` — администратор панели внутри контейнера (не связан с пользователями хоста);
* `-e ServerID=xxxx -e Serial=YYYY-BBBB-CCCC-DDDD -e ServerName=video.company.name` — автоматическая регистрация при старте (Serial — регистрационный ключ **без первых 4–5 символов**);
* `-e ServiceAddress` — внешний адрес;
* `-e INIT_DB=true` — пересоздать БД (необратимо, только для восстановления из бэкапа).

Монтировать обязательно `/opt/trueconf/server/var/lib` (БД, настройки, сертификаты). Для доступа к 4309 извне нужно добавить `-p 4309:4309` (в базовом примере его нет) либо использовать `--network=host`.

### 4.5 Регистрация и активация

1. Открыть панель: `http://<ip>/` (или `:8888`), войти OS-логином из `tcadmins` (в Docker — `ADMIN_USER`).
2. Ввести **регистрационный ключ** из письма → «Регистрация». Free регистрируется **только онлайн**; нужен исходящий TCP 4310 к `reg.trueconf.com`.
3. После успешной регистрации вверху панели — `running, registered`, все службы стартуют автоматически.
4. **Интернет обязателен постоянно** (для Free). При обрыве — таймер 12 ч, затем сервер отключается до восстановления связи.
5. Ключ привязан к «железу»: **модель CPU, объём диска, ОС**. Смена любого из этих параметров (в т.ч. пересоздание контейнера/ВМ с другими дисками) → ошибка HW key → нужна перерегистрация/сброс привязки через вендора. Смена мажорной версии (5.4→5.5) тоже требует перерегистрации.
6. Для Docker: **нельзя** управлять контейнером через `docker compose up/down` — пересоздание контейнера ломает лицензию. Только `docker compose start/stop` или `docker start/stop`.

### 4.6 HTTPS (нужен для WSS и «взрослых» функций)

Панель → **Web → Settings / HTTPS**: загрузить сертификат (`tls.crt` + `tls.key`, только .crt) или выпустить Let's Encrypt (нужен публичный домен), указать внешний адрес сервера. Для чистого теста в LAN можно остаться на `ws://` + 4309 и не трогать сертификаты.

## 5. После установки: бот, Chatbot Connector, проверка

### 5.1 Учётная запись бота

1. Панель → **Пользователи** → добавить пользователя (логин + пароль), режим **Registry** (или LDAP — тоже поддерживается).
2. Отдельной «роли бота» нет: бот — обычный пользователь. Права в чатах определяются ролью участника (owner/admin/user/writer для каналов).
3. Бот обязан быть пользователем **этого** сервера; федеративные и гостевые учётки для Chatbot API не подходят.
4. Форматы логина: `user`, `user@video.example.com`, `domain\user`, `domain\user@server.loc`.
5. Если на сервере отключён вход по паролю (NTLM/Kerberos/MFA) — с 5.5.3 нужен OAuth 2.0: приложение в **API → OAuth2** с правом `version:read`, затем трёхшаговый обмен токена (`/api/v4/oauth2/token` → `/bridge/api/client/v1/auth/web_rest_api_token` → `/bridge/api/client/v1/auth/token`).

### 5.2 Включение Chatbot Connector

Включать нечего: **`trueconf-bridge`** уже установлен и запущен вместе с сервером. Проверка на сервере:

```bash
systemctl status trueconf-bridge --no-pager
ss -ltnp | grep -E '4309|4307|:443|:80'
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:4309/bridge/api/client/v1/oauth/token
```

Если 4309 слушает только `127.0.0.1` — для n8n с другой машины либо пробрасывать порт/менять bind, либо идти через WSS на 443.

### 5.3 Проверка «бот отвечает» (curl)

**Шаг 1 — получить identification token (JWT):**

```bash
curl -i -X POST http://127.0.0.1:4309/bridge/api/client/v1/oauth/token \
  -H 'Content-Type: application/json' \
  -d '{"client_id":"chat_bot","grant_type":"password","username":"bot","password":"<пароль>"}'
```

Ожидаемо: `HTTP/1.1 201 Created` и JSON `{"access_token":"...","token_type":"JWT","expires_at":...}`. `400 invalid_grant` — неверный логин/пароль; `200`-ошибка вместо 201 — смотреть тело.

**Шаг 2 — WebSocket + auth.** Быстрая проверка через `python -m websockets` / `wscat`:

```bash
npx wscat -c ws://127.0.0.1:4309/websocket/chat_bot/ -s json.v1
> {"type":1,"id":1,"method":"auth","payload":{"token":"<JWT>","tokenType":"JWT","receiveUnread":false}}
```

Ожидаемо ответ `{"type":2,"id":1,"payload":{"userId":"bot@<server>/<hash>"}}`. Дальше — `sendMessage`/`getChats` по документации Chatbot API.

**Шаг 3 — «бот отвечает» end-to-end.** Отправить боту сообщение из клиента TrueConf (или создать чат через API) и убедиться, что приходит событие `newMessage`; ответить командой `sendMessage` и увидеть сообщение в клиенте.

Для n8n: учётка бота = server URL/host, порт, логин, пароль (или JWT), признак TLS. При самоподписанном сертификате — либо `NODE_TLS_REJECT_UNAUTHORIZED=0` в контейнере n8n (только тест!), либо смонтировать CA, либо тестировать по `ws://`.

## 6. Ограничения и подводные камни тестового стенда

| Риск | Суть | Как обойти |
|---|---|---|
| **Интернет для лицензии** | Free обязан держать TCP 4310 к `reg.trueconf.com`; прокси не поддерживается; офлайн-регистрации нет | Убедиться, что с хоста стенда есть исходящий 4310 (проверить `nc -vz reg.trueconf.com 4310`); иначе Free не зарегистрируется/отключится через 12 ч |
| **Корпоративная почта** | Ключ выдают только на corporate e-mail, форма ручная, письмо до 15 мин | Заранее согласовать адрес; заложить ожидание в план |
| **Привязка к «железу»** | Смена CPU/диска/ОС, пересоздание контейнера, апгрейд мажорной версии → HW key failed | Не пересоздавать ВМ/контейнер; для Docker — только start/stop; зафиксировать параметры ВМ до регистрации |
| **Самоподписанный сертификат** | Node.js/ws в n8n отвергает self-signed; WSS не заведётся «из коробки» | Тест по `ws://…:4309` внутри LAN; либо CA в контейнер n8n; либо `NODE_TLS_REJECT_UNAUTHORIZED=0` (не для прода) |
| **Доступ по IP** | Сервер работает по IP, но **Server Name нельзя задать IP**; для WSS имя в сертификате должно совпадать с адресом подключения | Для LAN-теста — plain WS; для WSS — DNS-имя (можно локальную запись в hosts) и сертификат с этим SAN |
| **DNS/домен** | Полноценная работа (планировщик, WebRTC, гостевые ссылки, push) требует FQDN + валидный сертификат | Для теста Chatbot API не требуется; не тратить время на Let's Encrypt без публичного домена |
| **Лицензия на ботов** | Отдельной нет; боты едят online-лицензии (во Free 1000) и WS-соединения (лимит 128) | Достаточно; следить за 128 при нагрузочных тестах |
| **10 PRO во Free** | Групповые конференции — только 10 участников | Для чат-ботов неважно; не строить тесты конференций на Free |
| **Занятые 80/443** | Если на хосте уже есть nginx/traefik/Apache — конфликт с веб-сервером TrueConf | Не ставить рядом с веб-сервером; либо менять порт панели (listen.conf/manager.toml), но 443 всё равно нужен для WSS |
| **Память** | Официально 16 ГБ; на слабой ВМ сервер работает, но без гарантий | Для теста 4 vCPU / 8 ГБ обычно достаточно; не грузить конференциями |
| **ALT: имя пользователя** | Нельзя OS-пользователя `trueconf` | Проверить `id trueconf` до установки |
| **Docker Desktop на Windows** | Может быть не запущен (проверено: демон не отвечает), WSL2, проброс портов, Windows Firewall, засыпание dev-машины | Запустить Docker Desktop, `-p` на 192.168.0.10, разрешить порты в firewall, отключить сон |
| **Пакеты вне официального списка** | Ubuntu/RHEL/Rocky — «не поддержано» | Не использовать для стенда, кроме ALT/Debian/Astra/РЕД ОС/CentOS Stream |

## 7. Варианты размещения тестового сервера

Исходные данные: LAN 192.168.0.0/24; n8n — 192.168.0.11 (ALT Linux 11.1, SSH+sudo есть); свободные хосты .6 (Debian 10), .7 и .18 (ОС неизвестна) — **доступов нет**; гипервизора с доступами нет; Windows dev-машина — 192.168.0.10 (Docker Desktop установлен, но **демон сейчас не запущен** — проверено).

### Вариант A. Установить на 192.168.0.11 рядом с n8n (ALT Linux 11.1)

*Плюсы:*
* ALT **официально поддерживается**: «Альт Сервер c10f1 / 10 / 11», в зеркале вендора есть ветка `altlinux/p11`.
* n8n и TrueConf на одном хосте → **`127.0.0.1:4309`**, plain `ws://`, никаких сертификатов, DNS и проброса портов. Это ровно тот сценарий, который документация называет «локальное подключение к TrueConf Bridge».
* Не нужны новые машины, доступы, согласования; откат — `apt-get remove`.

*Минусы и риски:*
* На рабочий хост n8n добавится **7 служб + PostgreSQL**, порты 80/443/4307, диск под БД и записи.
* Официально нужны 4 vCPU / 16 ГБ RAM; если хост слабее — это отклонение от требований (для теста приемлемо, но с оговоркой).
* Нельзя ставить на машину с уже работающим веб-сервером на 80/443 (nginx/traefik перед n8n — частая конфигурация; нужно проверить заранее).
* Любые работы с TrueConf (перезагрузка служб, обновление) задевают n8n, и наоборот.

*Оценка трудозатрат:* **1,5–3 часа** (30–60 мин на форму/ключ/скачивание, 20–30 мин установка и регистрация, 40–60 мин HTTPS/бот/проверка curl+WS), плюс время на согласование установки на рабочий хост.

### Вариант B. Отдельная ВМ/хост на Debian 12 (или Ubuntu)

*Плюсы:* чистая изоляция, «эталонная» поддерживаемая ОС, ничего не ломаем на n8n; проще воспроизвести и потом снести.

*Минусы:* **гипервизора с известными доступами нет**; .6 — Debian 10, который **не входит** в список поддерживаемых (минимум Debian 11) и доступа к нему нет; .7/.18 — ОС неизвестна, доступов нет. Значит, вариант требует либо появления доступа/гипервизора, либо нового хоста.

*Оценка трудозатрат:* **3–5 часов** + время на получение доступа/железа (может быть днями). Как «основной» план — не проходит по входным условиям.

### Вариант C. Windows dev-машина 192.168.0.10 (Docker Desktop)

*Плюсы:* не трогает ни n8n, ни прод-инфраструктуру; официальный Docker-образ `trueconf/trueconf-server`; снос — `docker rm -f`; n8n ходит на `192.168.0.10:4309` (или WSS на 443).
*Минусы:* Docker Desktop сейчас **не запущен** (проверено: `docker version` → нет соединения с `dockerDesktopLinuxEngine`), нужно поднять и дать WSL2 ресурсы; dev-машина может уходить в сон; **пересоздание контейнера ломает привязку лицензии** (нельзя `compose down/up`, только start/stop); Windows Firewall должен пропустить 80/443/4307/4309 с LAN; при переустановке Docker/смене диска — перерегистрация.
*Альтернатива внутри C:* нативный Windows-инсталлятор (Win 11 Pro подходит) — но тогда 5 служб в системе dev-машины и нет тихих ключей.

*Оценка трудозатрат:* **0,5–1,5 часа** (запуск Docker Desktop, pull образа ~2–4 ГБ, `docker run`, регистрация, бот, curl).

### Сводная таблица

| | A: .11 + ALT | B: отдельная ВМ Debian | C: Docker на .10 |
|---|---|---|---|
| Официальная поддержка ОС | да (Альт Сервер 10/11) | да (Debian 12) | да (Docker) |
| Нужны новые доступы/железо | нет | **да** | нет |
| Изоляция от n8n | низкая | высокая | высокая |
| TLS/сертификаты для бота | не нужны (localhost) | нужны или plain ws | нужны или plain ws |
| Трудозатраты | 1,5–3 ч | 3–5 ч + ожидание | 0,5–1,5 ч |
| Риск для рабочего n8n | средний | нет | нет |
| Долговечность стенда | высокая | высокая | средняя (dev-машина) |

### Рекомендация

1. **Основной вариант — A (192.168.0.11)**, если на хосте ≥8 ГБ RAM, свободны 80/443/4307 и нет веб-сервера на 80/443. Причина: единственный доступный официально поддерживаемый Linux + `ws://127.0.0.1:4309` без TLS/DNS — это снимает 80% типовых проблем интеграционного теста Chatbot API и даёт самый короткий путь до первого «бот ответил». Установку делать в окно, когда n8n не критичен, и сразу зафиксировать параметры (не менять диск/ОС), чтобы не слетела HW-привязка.
2. **Если хост .11 слабый или 80/443 заняты — вариант C (Docker Desktop на 192.168.0.10)**: полчаса-час, полная изоляция, снос одной командой. Обязательно: `--restart unless-stopped`, фиксированное имя контейнера, **не** использовать `docker compose down/up`.
3. Вариант B держать в резерве: он станет лучшим, как только появится доступ к гипервизору или к .7/.18 (и если там Debian 11+/Ubuntu). Тогда стенд можно сделать «одноразовым» и не трогать ничего рабочего.

### Чек-лист запуска (порядок действий)

1. Согласовать корпоративную почту → заполнить форму на <https://trueconf.com/downloads/trueconf-server/> → получить ключ (≤15 мин).
2. Проверить хост: RAM/CPU/диск, `ss -ltnp | grep -E ':(80|443|4307|4309)\b'`, `id trueconf`, наличие веб-сервера.
3. Проверить исходящий доступ: `nc -vz reg.trueconf.com 4310` и `443`.
4. Скачать пакет под ОС (Debian/ALT — `.rpm`, Astra — `.deb`) или `docker pull trueconf/trueconf-server:stable`.
5. Установить; открыть панель `http://<ip>/`; зарегистрировать ключом; дождаться `running, registered`.
6. Создать пользователя-бота (логин/пароль), записать в секреты n8n.
7. Проверить `systemctl status trueconf-bridge`, `curl` токена (201), WS `auth` (ответ с `userId`).
8. Прогнать end-to-end: сообщение боту → событие → ответ; зафиксировать версию сервера (`5.5.x`), версию `python-trueconf-bot`/ноды и лимиты (128 WS, JWT 1 мес).
9. Задокументировать: IP, порт, логин бота, версия, дата продления Free-лицензии (через год).
